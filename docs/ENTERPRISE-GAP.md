## 0. 结论摘要

start1921 是一个**建立在研究型 MVP 之上、已具备相当多生产化特征**的项目：证据可回溯到 PDF 物理页、六层分离的评测体系、硬化过的容器部署、访客隔离与配额、1000+ 测试与严格类型检查，这些在同类项目中并不常见。

但它距离"企业级 RAG 平台"仍差一个完整阶段，差距集中在三点，而不是"功能做得不够多"：

1. **答案可信度没有闭环**。生产链路已主动移除引用/页码/日期/未引用事实校验（BC-043），模型可以输出不存在的引用与错误日期并原样交付；同时 13 题真实运行整题通过率仅 3/13。这是企业评估的第一道红线。
2. **可靠性工程基本空白**。单实例单 worker、无连接池、无指标/追踪/告警、无自动化备份与恢复演练、评测不参与发布决策。系统"能跑"，但无法承诺 SLA。
3. **质量无法用数据背书**。30 题 Golden 只完成 20 题、其中 8 题人工批准，正式成绩为 `N/A`；仓库内没有 CI，质量门禁只存在于开发者本机的 PowerShell 脚本里。

用成熟度语言表述：**当前处于 L2（可演示/小规模对外）到 L3（内部生产）之间，尚未进入 L4（企业级）**。功能广度可以后补，可信度与运维底座拖不得。

## 1. 评估口径

### 1.1 成熟度分级

| 等级 | 定义 | 判据 |
| --- | --- | --- |
| L1 原型 | 能回答，结果不可复现 | 无评测、无版本化、手工运行 |
| L2 可演示 | 有完整链路，可对外小规模使用 | 有测试与部署，质量依赖人工观察 |
| L3 内部生产 | 可托付给内部用户 | 有门禁、有监控、有备份、有明确边界 |
| L4 企业级 | 可承诺 SLA 与合规 | 多租户/权限/审计、SLO、容灾、变更治理 |
| L5 平台化 | 支撑多业务域自助接入 | 自助接入、配额计费、插件生态 |

### 1.2 证据来源

本文引用的量化结论来自仓库既有产物，按可信度排序：

1. `evals/golden/observations/**` 下的冻结观测与复核记录（带指纹与人工裁定）；
2. `data/reports/**` 下的运行报告；
3. `deploy/**` 的部署配置与上线验证记录；
4. 代码与配置本身。

**未使用**任何本次新跑的数据；凡"约/估计"字样均为工程判断，不冒充测量值。

## 3. 已经达到企业级的部分

评估必须避免只列缺点。以下能力是项目的真实资产，后续改进应保留而不是重写：

### 3.1 证据可追溯

- 每个答案事实可映射到 `document_id + pdf_page`，引用含文献名、卷次、PDF 页码与短引文；
- `EvidenceRegistry` 在请求级发放稳定 `E1..En`，补检与任务合并不会重排编号；
- `research_plan` 与 `execution_summary` 暴露真实任务图、依赖、增补次数、阶段用量与停止原因。

这是"可审计问答"的基础，很多企业 RAG 项目在这里是缺失的。详见 [RAG 实现说明](../RAG-IMPL.md) 第 1、10 节。

### 3.2 分层评测体系

Golden v2 把一次问答拆成 routing / retrieval / ranking / candidate-context / generation / citation 六层，并实现了：

- `metric_status{value, evaluable, reason}`，不可评不按 0 分计入分母；
- dataset SHA、代码指纹、索引与 embedding 身份、RRF/Top-K 参数全部落盘；
- 比较器区分"可比较"与"可归因"，索引 manifest 不足时明确禁止把 delta 归因于 chunking/embedding；
- 固定候选池 nDCG 与稳定 evidence unit，避免"同一页多 chunk 重复吃分"。

这套设计比多数商业 RAG 的评测严谨。详见 [Golden 评测说明](../evals/golden/README.md)。

### 3.3 部署硬化

[`deploy/compose.yaml`](../deploy/compose.yaml) 已具备：只读根文件系统、`cap_drop: ALL`、非 root UID 10001、数据库与 Qdrant 仅内网、内存/CPU/pids 限额、健康检查、日志轮转、`restart: unless-stopped`。

`/api/health` 与 `/api/ready` 分离存活与依赖就绪，`/api/ready` 会实际执行一次向量检索，而不是只返回 200。

### 3.4 匿名隔离与配额

HttpOnly `__Host-` cookie、CSRF、按 `visitor_id` 隔离会话、跨访客统一 404、visitor/IP/global 三级日配额与 token 预算。在"不做登录"的产品定位下，这套隔离是合格的。

### 3.5 代码质量基线

mypy `disallow_untyped_defs`、Ruff（E/F/I/UP/B/SIM）、Pydantic 数据契约、1000+ 测试（[badCase.md](../badCase.md) 记录 1066 项）、7 份专题文档。文档详细程度超过多数商业项目。

## 4. 功能复杂度差距

### 4.1 答案可信度（最高优先级差距）

| 现状 | 风险 |
| --- | --- |
| 生产链路不做引用编号、页码、日期、未引用事实校验，也不因校验失败降级（BC-043） | 模型伪造 `[E99]`、写错日期、给出无出处结论时，系统原样交付 |
| `citations` 只回显模型写出的编号；没写就是空列表 | 前端"无引用"与"无证据"不可区分，用户无法判断可信度 |
| `evidence_status` 只剩 `supported/partial/no_evidence` 三态 | 需求基线的五类状态与独立 `conflicts` 字段未实现 |
| 无 claim 级蕴含校验、无来源冲突检测（FR-ANS-005） | 冲突史料会被静默合并成单一结论 |

[badCase.md](../badCase.md) BC-043 自己写了"残留风险：模型幻觉、伪造页码和错误日期不再被生产链路拦截；引用列表可能为空"。**这是当前最需要修的一条**，也是企业采购/合规评审的第一问。

需要说明的是：BC-043 的动机（旧校验误伤正常回答、失败即降级摘录）是合理的，问题在于**把"阻断式校验"整个删除，而不是改成"先观测、后拦截"**。

### 4.2 检索与上下文

- **无学习式重排**：当前"重排"= 分支内部排序 + RRF + 规则奖励 + 按页去重 + 时间覆盖；没有 cross-encoder（[RAG-IMPL.md](../RAG-IMPL.md) 第 15 节第 7 条）。
- **邻居扩展未启用**：`previous_chunk_id` / `next_chunk_id` 已写入每个 chunk，但在线召回从不使用（同节第 1 条）。
- **页内分片 + 按页去重**：一个事件跨页时不会合并；同页第二个相关片段会被去重规则挤掉（第 2 条）。
- **年份是"提及"而非"事件时间"**：回顾、比较、注释可能造成时间误归属（第 3 条）。
- **人物识别是别名字面匹配**：无 NER、无同音/简称/OCR 错字消歧（第 4 条）。
- **查询执行是串行的**：主查询与扩展查询依次执行，只有关键词/向量两分支用 `ThreadPoolExecutor(2)` 并发。

### 4.3 数据接入与索引生命周期

| 环节 | 现状 | 企业级要求 |
| --- | --- | --- |
| 文档接入 | 放入 `docs/` + 手工登记 `config/corpus_catalog.json` + CLI | 上传/删除 API、权限继承、连接器、失效同步 |
| 增量处理 | 抽取/OCR 按 SHA 复用；**索引全量重建** | 按文档 upsert、删除同步、embedding 版本迁移 |
| 发布隔离 | Qdrant alias 原子切换、关键词 generation 原子切换（做得好） | 构建/验证/发布分流水线，可回滚到指定 generation |
| 索引重建成本 | 22,338 chunk × 双索引全量 | 单文档更新 P95 < 5 分钟 |

现状意味着：**加一篇 PDF 就要重建两个索引**；换 embedding 模型等于全量离线重跑。当前 17 份文献规模可接受，10×-100× 语料下不可行。

### 4.4 平台能力广度

| 能力 | 现状 | 差距 |
| --- | --- | --- |
| 身份与权限 | 匿名 cookie，无账号 | SSO、RBAC、租户隔离、审计日志 |
| 管理后台 | 无 | 文档管理、复核队列产品化、用量看板 |
| 对外集成 | 17 个 `/api/*` 路由，无版本前缀 | `/v1`、API Key、SDK、Webhook |
| 反馈闭环 | 无 | 👍/👎/举报 + trace id → 标注 → 回归集 |
| 成本治理 | `usage_daily` 等表已记录用量 | 租户预算、熔断、模型路由、成本看板 |
| 交付体验 | 引用为 `<details>` 折叠文本 | 跳转 PDF 页、导出、分享 |
| 领域泛化 | 1921—1978 硬编码在配置与 prompt | 知识域配置化，支持第二语料域 |

结构化研究层（人物/事件/关系/复核队列）其实做得不浅，但**组织任职只有 CLI/API 入口，产品上不可达**；事件抽取是离线批处理，人工复核依赖脚本与本地工作台。

## 5. 架构复杂度差距

### 5.1 运行形态：单进程单体，`--workers 1` 是架构约束

- `HistoryResearchWorkflow`（LlamaIndex `Workflow`）直接跑在 uvicorn 进程内；run 状态、`BoundedSemaphore`、embedding 模型都在进程内，多 worker 会导致并发上限失效与模型重复加载。
- [Dockerfile](../deploy/Dockerfile) 显式 `--workers 1`；[compose](../deploy/compose.yaml) 单副本，1 CPU / 1 GiB。
- 没有任务队列：长问题（实测最长 31.6s）与 SSE 会占住唯一 worker；索引构建在宿主机手动执行，与线上服务共享文件系统卷。

这个形态在"单租户、小语料、低并发"下是**正确选择**，但它是容量天花板，不是可调参数。

### 5.2 数据访问：没有连接池

[`db_backend.py`](../app/history_agent/db_backend.py) 的 `database_connection()` 每次调用都 `psycopg.connect()` 新建连接，用完关闭。一次问答通常要开多次连接（会话读取、配额扣减、结构化查询、健康检查），连接建立包含 TCP + SCRAM 认证开销。

`max_connections=30` 是硬顶，没有 pgbouncer。并发上升后，瓶颈会先出现在连接而不是 CPU。这是**低成本、高收益**的待修项。

### 5.3 自研组件风险

| 组件 | 现状 | 风险 |
| --- | --- | --- |
| PostgreSQL 内手写倒排 | `keyword_postings(generation_id, rowid, term, positions[])` + 应用层 BM25 + jieba 预分词后的词位索引 | 22k chunk 可行；百万级就是自研搜索引擎，正确性与性能都要自己扛 |
| Qdrant 精确检索 | `search_params={"exact": True}` 暴力检索 | 线性扫描，规模上不去 |
| SQL 方言层 | `qmark_to_pyformat` 手写 SQL 词法器处理注释/引号/`E''`/dollar-quote/`%` | 历史迁移产物，属"能跑但别碰"的代码，安全与正确性双重风险 |
| schema 迁移 | 代码内幂等 DDL（`db.py`、`context.py`、`keyword_postgres.py` 各自 CREATE/ALTER） | 无 Alembic、无 downgrade、无迁移测试；测试是新建 schema，**老库升级路径未验证** |

### 5.4 模块边界

- God modules：`cli.py`（1775 行）、`evaluation/golden.py`（2061 行）、`answering/context.py`（1299 行）、[`web/app.py`](../app/history_agent/web/app.py)（915 行，同时管路由、访客、CSRF、配额、SSE、会话 CRUD）。
- 两套评测框架并存：`pilot_*`（约 20 个模块）与 `golden.py`，文档已声明"v1/v2 不可混用"，长期存在口径漂移风险。
- 领域模型与 LlamaIndex 类型（`Node`、`BaseRetriever`、`Workflow`）强绑定；适配层存在，但框架升级（0.14 → 0.15）仍是结构性风险。

## 6. 可用性差距

### 6.1 冗余与容灾

| 项 | 现状 |
| --- | --- |
| 应用 | 单容器、单 worker，无副本、无 failover |
| PostgreSQL | 单实例（Compose 内 single node），无流复制、无 PITR |
| Qdrant | 单节点，无副本 |
| 备份 | `pg_dump` + snapshot 全手工，无定时任务、无异地副本 |
| 恢复 | 无演练记录、无 RPO/RTO 定义、无恢复清单版本化 |

### 6.2 性能

需求基线：普通检索 P95 ≤ 2s，完整问答 P95 ≤ 15s。

13 题实测（（历史记录已清理））：

| 路径 | 均值 | 中位 | 最大 |
| --- | ---: | ---: | ---: |
| 组件检索墙钟 | 1,898 ms | 1,802 ms | 2,681 ms |
| 完整回答墙钟 | 17,557 ms | 15,130 ms | 31,621 ms |

样本仅 13 题且各题只测一次，不能当 P95 用；但**中位数已踩线、最大值翻倍于目标**，且每题平均 3.4 次 HTTP 请求（13 题 44 次）、平均约 8,900 token。延迟主要由模型调用轮次驱动（查询理解 → 检索反思 → 分组生成 → 综合 → 一次修复），不是检索本身。

### 6.3 可观测性

当前只有 JSON 结构化日志，**没有**：

- 指标（QPS、错误率、延迟分位、检索分支可用性、LLM 错误码分布、预算耗尽率、单题 token 成本）；
- 分布式追踪（request id 未贯穿 workflow 各 step、检索分支、模型调用）；
- 错误聚合/告警（无 Sentry 类工具）；
- SLO/SLI 定义与看板。

`/api/health`、`/api/ready` 只给布尔，运维无法回答"现在慢在哪里、错在哪一步"。这是"能不能承诺 SLA"的分水岭。

### 6.4 过载与降级

- LLM 并发 2 + 90s 请求预算；过载时表现为**预算耗尽 → 摘录兜底**，而不是明确的 429 或排队反馈。
- 无 per-IP 秒级限流（[nginx.conf.example](../deploy/nginx.conf.example) 只在注释里建议 `limit_req`）；日配额挡不住瞬时突发。
- 单供应商：DeepSeek 故障即全站降级，无第二 provider、无模型网关、无熔断。

值得肯定的是：规划失败有同流程保守计划、单检索分支失败有 `degraded_components` 降级、SSE 断连会取消预算与 workflow 并吞掉未观察异常。

### 6.5 发布与回滚

`dc build app` → `dc up -d --no-deps app`，回滚靠手工改 `START1921_APP_IMAGE`。无蓝绿/金丝雀、无迁移前置检查、无发布前自动 smoke、**评测结果不参与发布决策**。镜像按 tag 而非 digest 固定（部署文档自承）。

### 6.6 产品可用性

会话列表、置顶、重命名、软删除 30 天恢复、滚动摘要、SSE 增量渲染都可用，单用户体验合格。缺：引用跳转原文、导出、分享、反馈、多端同步（匿名 cookie 换设备即丢历史）。

## 7. 可维护性差距

### 7.1 质量门禁

- **无 CI**：仓库没有 `.github/workflows`，唯一门禁是本地 [scripts/check.ps1](../scripts/check.ps1)（ruff → mypy → pytest → node）。没有 PR 门禁、nightly、覆盖率阈值、依赖更新、密钥扫描、镜像扫描/SBOM。

## 9. 改进路线图

### 9.1 阶段 0：止血与门禁（1–2 周）

| # | 任务 | 交付物 | 验收标准 |

| 0.1 | 生产侧"软校验"：记录 `citation_id` 合法性、页码存在性、日期与引用一致性、未引用事实比例，**不阻断** | 指标字段 + 日志事件 | 连续 2 周可查询分布；误伤率可量化 |

## 10. 如果只能做三件事

1. **生产引用/事实软校验 + 反馈闭环** → 解决"能不能信、能不能审"。
2. **CI 门禁 + 30 题 Golden 冻结** → 解决"质量可证、回归可挡"。
3. **指标/追踪/告警 + 备份演练** → 解决"敢不敢托付"。

这三件完成后，项目从"优秀的研究型 Demo"变成"可托付的内部生产系统"；多租户、管理后台、模型网关都可以在此之后按业务节奏补。

粗估：**单租户内部生产可用约 1–2 个月（阶段 0+1），企业级平台约一个季度以上**。功能广度可以后补，可信度与运维底座拖不得。
