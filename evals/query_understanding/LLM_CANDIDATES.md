# LLM 实体候选生成（shadow，2026-10-30）

## 目的

词典和模糊匹配覆盖不了 OCR 错字、繁简差异和未收录写法。这一步让 LLM 在**实体索引的封闭集合内**为未识别 span 提名候选，再交给确定性校验；LLM 不能创造实体。

链路：

```text
词典 + 模糊检测
  → 未覆盖 span
  → LLM 只从实体索引中提名 entity_id
  → 校验：mention 在问句中、长度 2–12、无功能词、entity_id 在索引内、canonical 一致
  → 合并后重新锚定
```

## 用例

`candidate_cases.json`：8 条，6 条变体 + 2 条对照。

变体包括：`毛润芝`、`刘伯成`、`周恩來/重慶`、`朱徳`、`彭徳怀`、`整風`。

## 结果

| 指标 | 词典 + 模糊 | 再加 LLM 候选 |
|---|---:|---:|
| Precision | 88.9% | **93.3%** |
| Recall | 53.3% | **93.3%** |
| F1 | 66.7% | **93.3%** |

LLM 补上的典型项：

- `毛润芝 → 毛泽东`
- `刘伯成 → 刘伯承`
- `周恩來 → 周恩来`
- `重慶 → 重庆`
- `朱徳 → 朱德`
- `彭徳怀 → 彭德怀`

只有 `整風` 仍未命中：LLM 对“延安整風”直接 abstain，没有映射到 `延安整风`。这是下一步要补的繁简/异体归一问题。

## 安全边界

- 候选必须来自实体索引的 `entity_id`；不在索引内直接拒绝。
- `mention_text` 必须在问句中出现、长度 2–12、不能包含“在/的/了/和/与/期间/参加/什么/哪些/年/月/日”等功能词。
- LLM 返回空占位（entity_id 为空）会被忽略，不导致整次失败。
- 解析失败时重试一次；仍失败则回退词典结果。
- 不修改线上检索；当前只做 shadow。

## 成本与限制

- 8 条用例只对未覆盖 span 调用，未覆盖时为空调用；实际请求少于 8 次。
- LLM 输出有非确定性；同一用例可能一次成功、一次 abstain，需要重试和缓存。
- 实体索引仍是 v1 种子（145 条），索引外实体不会因为 LLM 而被识别。
- 繁简/异体字未做确定性归一，完全依赖 LLM，稳定性不足。

## 下一步

1. 加繁简/异体字归一（`風→风`、`慶→庆`、`徳→德`），减少对 LLM 的依赖；
2. 把候选生成接进 `entity_linking` 的 shadow 主流程，记录每次 LLM 调用与候选；
3. 扩大变体用例到 30–50 条，验证 precision 不会因 LLM 误配下降；
4. 通过后再考虑接入查询臂，且只在别名/错字命中时启用。
